# D-0020 ログインは自分で作り、セッション（Cookie にはランダムな合言葉、記録は DB）にする

日付: 2026-10-27

## 決定
- ステップ7のログインは、外部サービスを使わずに自分で作る。
- ログインの状態はセッションで持つ。Cookie には意味のないランダムな文字列（合言葉）だけを入れ、「どの合言葉がどのユーザーか」はサーバーの DB に保存する。
- パスワードのハッシュに使うライブラリと、セッションをどこまで自分で書くか（ライブラリに任せるか）は、7-3・7-4 の始めに選択肢を示して決める。

## 理由
- 画面と API を同じ Express が配信していて、サーバーは1台。Cookie がそのまま使え、JWT の強み（DB を引かずに確かめられる、別のサーバーやアプリと分け合える）が活きない。どの API もどうせ DB を引くので、セッションの確認で1回増えても差はほぼない。
- ログアウトや追い出しが、DB の行を消すだけで確実にできる。
- 仕組みがすべて見える。ログインの記録を `psql` で確かめられ、ステップ6の SQL と外部キーの続きとして学べる（D-0018 の見込みどおり）。
- 外部サービスでよく使われる「短い期限の JWT ＋ DB に保存するリフレッシュトークン」の組み合わせも、セッションを知っていると理由が分かる。

## 却下した案
- 自分で作る＋JWT: 期限までは取り消せない（ログアウトしても、盗まれた JWT は使える）。秘密の鍵が漏れると全員分を偽造される。取り消せるようにすると結局 DB に保存が要る。
- 外部サービス（Auth0、Clerk、Firebase Authentication、Supabase Auth など）: 中身が見えず、学ぶのがサービスの設定方法になる。ユーザー情報を外部に預けるので、会社の決まりの確認が要る。7-7 で選択肢として紹介する。

## 補足
- 学習者から「JWT のほうが最近よく使われているのか」と質問があった。外部サービスや、画面と API を分ける構成で見かける機会は増えたが、JWT だけで済ませることは少なく、セッションも今も標準（Rails・Django・Laravel、Better Auth など）と説明した。
