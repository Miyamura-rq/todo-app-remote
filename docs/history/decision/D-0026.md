# D-0026 タグは tags と中間の表 todo_tag で持ち、他人のタグは2つの列の外部キーで止める

日付: 2026-10-28
補足する決定: D-0025（Issue の「決めてほしいこと」は学習者が決める）

学習者が決めたもの（Issue #1 の「決めてほしいこと」①②）。Claude は選択肢と基準を示し、レビューした。PR の本文には学習者が自分の言葉で書く。

## 決定
- タグは、タグそのものの表 `tags` と、ToDo とタグの組の表 `todo_tag`（多対多の中間の表）で持つ。
  - `tags`：`id`（主キー）、`name`、`user_id`（`users` を指す。`ON DELETE CASCADE`）。`UNIQUE (user_id, name)` で、同じユーザーが同じ名前のタグを2つ作れない。ほかのユーザーとは同じ名前でもよい。
  - `todo_tag`：`user_id`・`todo_id`・`tag_id`。主キーは組 `(todo_id, tag_id)`。
- 他人のタグ・他人の ToDo を付けられないことは、DB でも止める。`todo_tag` に `user_id` を持たせ、`FOREIGN KEY (todo_id, user_id) REFERENCES todos (id, user_id)` と `FOREIGN KEY (tag_id, user_id) REFERENCES tags (id, user_id)` にする。そのため `todos` と `tags` に `UNIQUE (id, user_id)` を足した。
- タグを削除したときは、ToDo は残り、そのタグだけが外れる（2つの外部キーとも `ON DELETE CASCADE`）。ToDo やユーザーを消したときも、`todo_tag` の行は一緒に消える。
- タグの名前の大文字・小文字は同じとみなす。サーバーで小文字にそろえてから保存する（7-3 のメールアドレスと同じ考え方）。
- 今ある DB は `todos` が変わるので作り直す（`CREATE TABLE IF NOT EXISTS` は既存の表を変えない）。

## 理由
- 文字列の列・配列の列では、同じ名前を DB の制約で止められず、他人のタグかも DB で確かめられない（Issue の完了条件を満たしにくい）。
- 中間の表の行を番号1つで指す必要がないので、組を主キーにした。同じ ToDo に同じタグが2回付かない。
- 学習者の理由：「タグは ToDo の付随機能なので、タグを消したときに ToDo まで消えると不便」。
- 2つの列の外部キーにすると、API の SQL で確かめ忘れても、DB が他人のタグを付けるのを止める。そのかわり `todos` の表が変わり、DB の作り直しが要る。

## 却下した案
- `todos` に文字列の列や配列の列（`TEXT[]`）でタグを持つ：上の理由。
- 中間の表に自分の `id` 列＋`UNIQUE (todo_id, tag_id)`：行を番号1つで指す必要がない。
- タグが付いているあいだは消せない（`RESTRICT`）、論理削除、ToDo ごと消す：使う人の予想と手間から a にした。
- 中間の表の `user_id` を消して、アプリの SQL だけで確かめる：学習者が DB でも守るほうを選んだ。
- 大文字・小文字を DB の `lower(name)` の `UNIQUE` 索引で同じとみなす：学習者はサーバーでそろえるほうを選んだ（画面の表示も小文字になる）。
