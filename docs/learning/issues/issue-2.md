ToDo リストを他のユーザーと共有できるようにし、他の人の変更がリロードせずに画面に反映されるようにします。研修の課題です。権限の設計（誰が何をしてよいか）と、サーバーから画面へ変更を届ける仕組み（SSE または WebSocket）を扱います。

## 背景

今の ToDo は 1 人のユーザーに属し（`todos.user_id`）、本人しか読み書きできません（`src/server/server.ts` の `requireLogin` と各 SQL の `user_id = $n`）。家族や同僚と同じリストを使うことはできません。画面は自分の操作のあとに `loadTodos()` で取り直すだけなので、他の人の変更はリロードするまで見えません。

## やること

### リスト

- ユーザーは複数の「リスト」を作れる。ToDo はどれか 1 つのリストに入る。
- 今ある ToDo は、ユーザーごとに作る最初のリストに移す。移し方（SQL）を PR に書く。

### 共有と招待

- リストの作成者（オーナー）は、メールアドレスを指定して他のユーザーをリストに招待できる。招待された人が承認するとメンバーになる。
- 権限は次の 2 種類にする。

| 権限 | できること |
|---|---|
| 編集 | ToDo の追加・完了・削除 |
| 閲覧 | ToDo を読むだけ |

- オーナーだけが、メンバーの招待・権限の変更・外すこと、リストの削除をできる。

### リアルタイムの反映

- 同じリストを開いている人の画面に、他の人の追加・完了・削除がリロードせずに反映される。
- SSE と WebSocket のどちらを使うかを選び、選んだ理由を PR に書く。

### 進め方

PR は分けてかまいません。たとえば「リストと ToDo の移行」「招待と権限」「リアルタイムの反映」の 3 本です。それぞれのマージ後に、アプリが動く状態にしてください。

## 完了条件

### 権限

- [ ] メンバーでないユーザーが、他人のリストの ToDo を API を直接呼び出して読めない・変更できない（どの API をどう呼び出して確かめたかを PR に書く）
- [ ] 閲覧の権限のメンバーが、API を直接呼び出して ToDo を追加・完了・削除できない
- [ ] オーナー以外が、招待・権限の変更・リストの削除をできない
- [ ] 存在しないユーザーのメールアドレスを招待したときに、そのアドレスが登録済みかどうかが応答から分からない（分からないようにした方法、または分かってよいと判断した理由を PR に書く）
- [ ] 上の 4 項目を、API を呼び出すテストで確かめている

### 移行

- [ ] 課題の前からある ToDo が、移行後もそのユーザーの最初のリストに残っている

### リアルタイムの反映

- [ ] ブラウザを 2 つ（別のユーザーでログイン）開き、片方で追加・完了・削除すると、もう片方にリロードせずに反映される
- [ ] メンバーから外されたユーザーには、そのリストの変更が届かなくなる
- [ ] サーバーを再起動したあと、画面がつながり直して変更を受け取れる

## 依存・順序

- ログイン・登録の画面ができている必要があります。
- タグと絞り込みの課題のあとに取り組む想定です。タグはリストのメンバーで共有するかどうかを決め、PR に書いてください。

## 別の Issue で検討するもの（スコープ外）

- 招待のメール送信（今回は、招待された人がログインしたときに画面で招待を見られればよい）
- 2 人が同時に同じ ToDo を変更したときの衝突の検出
- 担当者の割り当て、コメント
