## 1-1 クライアントとサーバー

### 考え方
- **クライアント**（頼む側）：ブラウザ
- **サーバー**（返す側）：リクエストを待ち受けて返すコンピューター／プログラム
- **必ずクライアントから頼む**。リクエストには必ずレスポンスが対になって返る
- サーバーが送るのは画面の**材料**（HTML / CSS / JS のテキスト）。画面を描くのはブラウザ
- クライアントとサーバーは**役割の名前**。1台の Mac で両方の役をすることもある（ステップ5）

| レストラン | Web |
|---|---|
| お客さん | クライアント（ブラウザ） |
| 注文 | リクエスト |
| 厨房 | サーバー |
| 料理 | レスポンス |
| 倉庫 | データベース |

### 完成した ToDo アプリでのデータの流れ
- 行き：ブラウザ → Express → PostgreSQL
- 帰り：PostgreSQL →「保存できた」→ Express →「追加できた」→ ブラウザ → 画面に表示
- **ブラウザは DB と直接話さない**。Express が「この操作を許してよいか」を確かめる門番になる（ステップ8）

### ステップ3で ToDo が再読み込みで消える理由
- ToDo が**ページのメモリ（JS の変数）**にしかないから。再読み込みでページが作り直されると捨てられる
- 残すには、ページの外（サーバーの先の DB）に置く必要がある

## 1-2 URL と DNS

### URL の各部分
例：`https://www.example.com:443/todos?done=false`

| 部分 | 例 | 意味 |
|---|---|---|
| スキーム | `https` | どの決まりで話すか（`https` は暗号化した HTTP） |
| ホスト名 | `www.example.com` | どのサーバーか |
| ポート | `:443` | サーバーの中の窓口（部屋番号）。https は 443、http は 80 が標準で省略される |
| パス | `/todos` | サーバーの中の何がほしいか |
| クエリ | `?done=false` | 追加の条件 |

### DNS
- コンピューター同士は **IP アドレス**（数字の住所）で相手を見つける
- **DNS は名前 → IP アドレスを調べる電話帳**
- 流れ：DNS に聞く → IP アドレスが返る → その IP アドレスのサーバーにリクエスト
- IP アドレスは変わることがある。名前で覚えて毎回引けば困らない

### localhost
| | IP アドレス | 意味 |
|---|---|---|
| `localhost` | `127.0.0.1` | **自分自身**。どのパソコンでも同じ。通信が PC の外に出ないので速い（ping 0.05 ms） |
| Wi-Fi の IP | `192.168.3.4`（例） | 家・会社のネットワークの中での住所。ルーターが割り当てる |

ステップ5の `http://localhost:3000` は「自分の Mac の中で動く Express の 3000 番の部屋」という意味。

### コマンド
| コマンド | 意味 |
|---|---|
| `nslookup 名前` | DNS に問い合わせて IP アドレスを表示する |
| `ping -c 1 名前` | 相手に1回だけ届くか試し、かかった時間を表示する |
| `ipconfig getifaddr en0` | Mac の Wi-Fi の IP アドレスを表示する |

## 1-3 HTTP のリクエストとレスポンス

### HTTP とは
ブラウザとサーバーが話すときの決まった書き方（注文票の書式）。中身はただのテキスト。

```
GET /todos HTTP/1.1          ← メソッド + パス
Host: localhost:3000         ← ヘッダー（補足情報）
（必要ならボディ）
```

```
HTTP/1.1 200 OK                       ← ステータスコード
Content-Type: application/json        ← ヘッダー

[{"id":1,"title":"牛乳を買う"}]       ← ボディ
```

### メソッド
| メソッド | 意味 | ToDo アプリでの例 |
|---|---|---|
| GET | 取得 | 一覧をもらう |
| POST | 作成 | 追加する |
| PUT / PATCH | 更新 | 完了にする |
| DELETE | 削除 | 消す |

1つの操作ごとに1つのリクエストを送る（完了 → 削除なら PATCH と DELETE の2回）。

### ステータスコード
| 番台 | 意味 | 例 |
|---|---|---|
| 2xx | 成功 | 200 OK、201 Created（新しく作った） |
| 3xx | 別の場所へ | 301 |
| 4xx | **頼んだ側（クライアント）の問題** | 400 Bad Request（入力がおかしい）、404 Not Found |
| 5xx | **返す側（サーバー）の問題** | 500 |

- 4xx か 5xx かで「直すべきはブラウザ側か、サーバー側か」を見分ける
- 番号を細かく分けるのは、ブラウザ側のコードが番号を見て動きを変えられるようにするため
- 空のタイトルを断るのは 400：サーバーは壊れておらず、ルールどおりに断っただけ（入力チェックはステップ8）

## 1-4 開発者ツールで通信を見る

### 手順（Chrome）
1. `Cmd + Option + I` で開発者ツールを開く
2. **Network** タブを選ぶ
3. ページを開き、一覧の行をクリック → **Headers** タブ

### example.com で見えたもの
| 項目 | 値 | 意味 |
|---|---|---|
| Request Method | `GET` | ページの取得を頼んだ |
| Status Code | `200 OK` | 成功 |
| Content-Type | `text/html; charset=utf-8` | 中身は HTML、文字コードは UTF-8 |

- `https://example.com/aaaa` → `404`
- **Content-Type** を見て、ブラウザは「画面に描く（HTML）」か「データとして扱う（JSON）」かを判断する
- **Response** タブでは、返ってきたテキストそのものが見られる

### ページ1つで大量のリクエスト
github.com を開くと約350個のリクエストが出た。

| Type | 中身 | 役割 |
|---|---|---|
| document | HTML | 骨組み |
| stylesheet | CSS | 見た目 |
| script | JavaScript | 動き |
| img など | 画像、フォント | 素材 |
| fetch / xhr | データ（JSON など） | ページを開いたあとに JS がデータだけもらう（ToDo 一覧の取得はこれ） |

## 1-5 フロントエンドとバックエンド

```
【ユーザーの PC】                       【サーバー】
ブラウザ（HTML / CSS / JS）  ── HTTP ──→  Express  ── SQL ──→  PostgreSQL
                             ←─ JSON ──             ←───────
  フロントエンド（ステップ2・3・4）       バックエンド（ステップ5・6）
```

| | フロントエンド | バックエンド |
|---|---|---|
| どこで動く | ユーザーのブラウザ | サーバー |
| 担当 | 見せる、操作を受け付ける | 確かめる、保存する、取り出す |
| 今回の技術 | HTML / CSS / TypeScript | Node.js + Express（TypeScript）、PostgreSQL |
| 中身 | **誰でも見られる・書き換えられる** | ユーザーからは見えない |

→ チェックはフロントだけでは安心できない。**必ずバックエンドでも確かめる**（ステップ8）。

### 技術の選択肢
**通信のやり方**
| 方式 | 特徴 | 向いているもの |
|---|---|---|
| **HTTP**（採用） | クライアントが頼んでサーバーが返す | 操作したときだけ通信するアプリ |
| WebSocket | つなぎっぱなし。サーバーからも送れる | チャット、同時編集、通話アプリの「着信」などの合図 |
| WebRTC（参考） | なるべく相手と直接つなぐ。多少欠けても待たない | 通話の声・映像 |

**API の設計**
| 方式 | 特徴 |
|---|---|
| **REST**（採用） | URL ＝ 対象、メソッド ＝ 操作。HTTP の知識がそのまま使える |
| GraphQL | URL は1つ。ほしいデータの形をクライアントが細かく指定する。複雑な画面向き |

ToDo アプリの REST API（予定）：
| やりたいこと | リクエスト | 成功時 |
|---|---|---|
| 一覧を取る | `GET /todos` | 200 |
| 追加する | `POST /todos` | 201 |

**選ぶ基準**：何を優先するか（速さ・確実さ・作りやすさ）、アプリの規模に合うか、学ぶ量。ToDo は「確実さ」優先で、0.1 秒の遅れは気にならない → HTTP + REST。

## ページが表示されるまでの流れ（ステップ1のゴール）
1. DNS で `github.com` を IP アドレスに変える
2. その IP アドレスのサーバーに、HTTPS で `GET` のリクエストを送る
3. サーバーが `200 OK` と一緒に HTML を返す
4. ブラウザが HTML を読み、そこに書かれた CSS・JS・画像を**それぞれ別のリクエストで**取りに行く
5. 全部そろったら、ブラウザが画面を描く

## つまずいたことと解決方法
| つまずき | 原因 | 解決 |
|---|---|---|
| localhost を Wi-Fi の IP だと思った | 「自分自身」を指す特別な住所を知らなかった | `ping localhost`（127.0.0.1）と `ipconfig getifaddr en0` を比べて違いを確認 |
| 削除のメソッドを PATCH と答えた | 問題文の「完了にして、さらに削除」の読み違い | 1つの操作 = 1つのリクエスト。削除は DELETE |
